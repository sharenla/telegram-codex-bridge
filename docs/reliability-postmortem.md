# Telegram Bridge 可靠性复盘

## 目标与结果

目标是：任何被受理的消息，在任何故障下都至少收到一条中文说明。
Phase 1–4 已围绕消息接收、执行、回复和重启恢复补齐反馈路径；三实例经过灰度部署，维护者确认版本、后端状态和出站队列正常。

## 根因与修复

以下每条均为「现象 → 根因 → 修复任务 → 代表提交」：

- 回复偶发永久丢失 → `sendMessage` 未纳入临时错误重试 → T2.1 → `b55b4fc`。
- 轮询卡住会自杀且不告知用户 → 网络错误与进程重启耦合 → T3.3/T3.4 → `32d1202`、`8043a59`。
- 启动时 app-server 长时间不出现 → 网络依赖的身份查询阻塞启动 → T3.1 → `bfb8c79`。
- 轮询抖动达到阈值就退出 → 卡死阈值误用于网络故障 → T3.3 → `32d1202`。
- 模型满载触发账号切换 → 满载文本混入账号故障模式 → T2.7 → `7b5045d`。
- 强杀留下长轮询和未落盘入站状态 → 关闭流程没有统一收尾与原子 inbox → T2.2/T2.3 → `6987247`。
- 实例锁会被系统临时目录清理或错误接管 → 锁位置不持久、持有者校验不足 → T2.8/T2.8a → `75cbedc`、`666dd97`。
- 群消息未定向时完全无提示 → 产品规则把未提及 bot 的消息视为不受理 → 设计保留；T4.4 统一已受理消息文案 → `3dd0f77`。
- 失联原因无法关联到时间和会话 → 日志无统一状态、恢复播报和出站可见性 → T3.3/T3.4/T4.6 → `32d1202`、`8043a59`、`e1c6972`。

## 已知限制

- 凭证被吊销或 bot 被删除时，同一凭证无法发出告警，必须由维护者恢复凭证。
- 未提及 bot 的群消息按设计不受理。
- 上游 5xx、模型满载、supervisor 告警、409 冲突、等待用户和永久拒绝等路径没有安全的线上制造条件，依赖测试与自然发生时观察。

## 运维要点

1. 灰度顺序固定为 `rv-prediction → 默认实例 → strategy-observation`；每批确认进程、启动三标记、代码哈希、持久锁和角色文件。
2. `/status` 重点核对 `codeVersion`、`telegramState`、`codexBackend`、`outboxQueued`、`outboxDiscarded`、`unreachableChats`、`clashFailover` 与实例的 `truthProfile`。
3. T4.9 崩溃演练只杀指定实例的 app-server 子进程，确认 bridge PID 不变、ack 变为中断提示、supervisor 没有新增 unhealthy restarting；命令只输出 PID，不输出完整进程参数：
   ```sh
   B=$(pgrep -f "telegram-codex-bridge-<instance>-service/index.js" | head -1)
   printf '%s\n' "$B"
   pkill -P "$B" -f "codex app-server"
   ```
4. 所有诊断先脱敏。统计 Telegram curl 时使用 `telegram[.]org` 等写法避免 grep 把自身命令行算进去；只报告数量，不打印 argv 或 URL。
5. 出现故障先看安装副本的 `DEPLOYED_REF`、启动日志和 `/status`，再按最近的阶段 tag 复核哈希。
